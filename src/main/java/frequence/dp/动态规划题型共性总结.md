## 分类原则：不要只按“几维数组”分类

一个DP题至少可以从三个维度分类：

1. **状态拓扑**：状态由什么参数确定，例如前缀长度、结尾位置、左右边界、棋盘坐标、容量或业务状态。
2. **状态值语义**：格子保存可行性、最优值、全部方案数、最优方案数，还是需要构造的结果。
3. **存储实现**：逻辑状态最终使用二维表、一维表、滚动数组还是常数变量保存。

这三者不能混为一谈。例如Q115同时是“双序列前缀DP”和“纯计数DP”；Q673同时是“一维位置结尾型DP”
和“最优值+最优方案计数”。把二维表压缩成一维表，只改变存储方式，不改变逻辑状态拓扑。

### 纯计数DP与“最优值+计数”的区别

Q115没有“更优或更差”，每个合法下标选择都属于答案：

```text
dp[i][j] = 不使用当前字符的方案数 + 使用当前字符的方案数
```

Q673先比较候选长度，只有达到局部最优长度的方案才有资格计数：

```java
if (candidateLength > length[i]) {
    length[i] = candidateLength;
    count[i] = count[j];       // 更优：覆盖旧计数
} else if (candidateLength == length[i]) {
    count[i] += count[j];      // 同样优：累加新来源
}
```

`count[i]`没有增加新的独立状态参数；状态仍由i确定，只是每个i同时保存“最优长度”和“达到该长度的
方案数”两个属性，可以实现为两个数组、`dp[n][2]`或`Info[]`。

[《一维DP核心总结.md》](./一维DP核心总结.md)；其中位置结尾型 DP 的详细推导另见
[《一维位置结尾型DP.md》](./一维位置结尾型DP.md)。

Q152 最大/最小双状态与股票 hold/cash 状态机的结构对比见

不是股票cash/hold那样的互斥业务状态，因此Q152不归入业务状态机DP。

## 动态规划的统一来源

动态规划通常从“尝试模型”开始：

```text
当前状态有哪些选择？
每种选择会进入哪个后续状态？
多个选择之间取最大、最小、求和还是逻辑或？
```

如果递归中相同参数组合会被重复计算，就可以记忆化；如果依赖方向明确，就可以改成表格 DP。

递归参数通常对应 DP 维度：

```text
process(index)                  -> 一维dp[index]
process(index, rest)            -> 二维dp[index][rest]
process(row, col)               -> 二维dp[row][col]
process(index, previousState)   -> 二维状态或多个一维状态
```

但参数能否消除取决于状态中是否存在支配关系、固定依赖或可复用的枚举规律。

## 写 DP 的六个步骤

1. **定义状态**：每一个维度和 `dp` 值分别代表什么。
2. **列出选择**：当前状态可以执行哪些决策。
3. **写转移方程**：每个选择依赖哪个已知状态。
4. **设置 base case**：空前缀、金额0、数组末尾等状态的答案。
5. **确定遍历方向**：必须保证依赖状态先于当前状态计算完成。
6. **确定答案位置**：是 `dp[n]`、`dp[0]`，还是所有状态的最大值。

最常见的错误不是方程本身，而是状态定义、初始化、遍历方向和最终答案位置不一致。

## 模型一：固定前驱线性 DP

代表题目：Q70、Q198。

状态只依赖固定数量的相邻状态：

```text
Q70：dp[i] = dp[i-1] + dp[i-2]
Q198：dp[i] = max(nums[i] + dp[i+2], dp[i+1])
```

共同点：

- 不需要枚举所有历史位置。
- 时间复杂度通常为 O(N)。
- 只依赖固定数量状态时，可以压缩成 O(1) 额外空间。

空间压缩时必须先计算当前值，再按照依赖顺序移动旧状态，避免提前覆盖。

## 模型二：递推构造

代表题目：Q118。

杨辉三角不是在多个方案中求最优值，而是按照已知递推关系构造完整结果：

```text
current[col] = previous[col-1] + previous[col]
```

共同思路仍然是“当前状态由已完成的前一层状态得到”，但输出本身要求保存所有行，因此空间无法压缩
为 O(1)。另外，`ArrayList` 的容量不等于逻辑长度，必须先 `add` 元素才能使用对应下标。

## 模型三：完全背包

代表题目：Q279、Q322。

共同点：

- 备选元素可以重复使用。
- 状态通常表示凑出某个目标值的最优答案。
- 一维空间压缩后，目标值必须**从小到大**遍历，使本轮刚更新的状态能够再次使用当前元素。

```java
for (int item : items) {
    for (int target = item; target <= capacity; target++) {
        dp[target] = Math.min(dp[target], dp[target - item] + 1);
    }
}
```

最小值问题需要设置可靠的不可达哨兵，例如 `amount + 1`，并避免从不可达状态执行 `+1`。

## 模型四：0-1 背包

代表题目：Q416。

每个元素最多使用一次。一维压缩后，目标值必须**从大到小**遍历：

```java
for (int num : nums) {
    for (int target = capacity; target >= num; target--) {
        dp[target] = dp[target] || dp[target - num];
    }
}
```

如果正序遍历，`dp[target-num]` 可能已经在本轮使用当前 `num` 更新过，导致同一个元素被重复使用，
错误地变成完全背包。

记忆对比：

```text
0-1背包：每个元素一次，容量倒序；
完全背包：元素可以重复，容量正序。
```

## 模型五：字符串切分 DP

代表题目：Q139。

定义：

```text
dp[i] = 前缀s[0,i)能否被合法切分
```

枚举最后一段的起点 `j`：

```text
dp[j]成立 && s[j,i)属于字典 -> dp[i]成立
```

这类题的共同模板是：

```text
固定右边界end；
枚举最后一个分割点start；
检查左侧前缀状态和当前片段是否合法。
```

类似题目包括分割回文串的最少切割次数、解码方法、字符串组成方案数等。

## 模型六：一维位置结尾型 DP

代表题目：Q300、Q152、Q32。

统一定义方式：

```text
dp[i] = 必须以位置i结尾的局部最优答案
```

该定义固定了右边界，保留后续转移所需信息。最终答案通常是全部结尾状态的最大值，而不一定是
`dp[n-1]`。具体的连续、子序列、跳跃前驱和多状态区别见《一维位置结尾型DP.md》。

## 从二维 DP 到一维 DP

空间压缩前必须回答两个问题：

1. 当前行只依赖上一行，还是也依赖当前行已经更新的位置？
2. 当前元素允许重复使用吗？

| 依赖关系 | 遍历方向 | 代表模型 |
|---|---|---|
| 只允许读取上一轮旧状态 | 倒序覆盖 | 0-1 背包 |
| 允许读取本轮新状态 | 正序覆盖 | 完全背包 |
| 只依赖固定前驱 | 保存若干变量 | 爬楼梯、打家劫舍、最大乘积子数组 |

不能只看到二维数组就机械压缩；遍历方向本质上是在控制“本轮的新状态是否可以被再次读取”。

## 高频错误汇总

| 错误 | 典型题目 | 修正原则 |
|---|---|---|
| `new int[n]` 后访问 `dp[n]` | Q279 | 状态下标范围是 `[0,n]` 时数组长度必须为 `n+1` |
| 临时答案计算完成但没有写回 `dp[i][j]` | Q416 | 每个 DP 格子必须在对应最内层循环完成赋值 |
| 使用不存在的 `||=` | Q416 | Java布尔复合赋值可用 `|=`，更清晰的是 `p = p || condition` |
| 混淆临时无穷大和题目无解值 `-1` | Q139、Q322 | 明确定义每种哨兵值的生命周期与语义 |
| 把 ArrayList 容量当成逻辑长度 | Q118 | 容量只影响扩容，元素必须通过 `add` 创建 |
| 0-1 背包容量正序 | Q416 | 倒序防止同一元素重复使用 |
| 完全背包容量倒序 | Q279、Q322 | 正序允许当前元素重复参与转移 |
| 最优答案默认取 `dp[n-1]` | Q300、Q152、Q32 | 如果方案可以提前结束，需要维护全局答案 |
| 记忆化使用 String 拼接状态键 | Q300 | 优先使用可压缩下标、数组或紧凑数值键 |

## 面试落地顺序

```text
1. 先写清递归含义或dp状态定义；
2. 写出不压缩的转移，保证正确；
3. 检查base case、依赖方向和答案位置；
4. 分析时间和空间复杂度；
5. 最后再做滚动数组、背包方向或专用二分等优化。
```

优先得到定义一致、可以验证的解法，比一开始追求最短代码或专用最优技巧更稳定。
