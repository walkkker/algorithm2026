# 双堆与滑动窗口中位数

## 1. 双堆解决什么问题

双堆适合维护动态数据集合的中位数：

- `small`：大根堆，保存较小的一半，堆顶是较小一半的最大值。
- `large`：小根堆，保存较大的一半，堆顶是较大一半的最小值。

始终维护两个不变量：

1. **顺序不变量**：`small` 中的有效元素都不大于 `large` 中的有效元素。
2. **大小不变量**：`smallSize == largeSize`，或者 `smallSize == largeSize + 1`。

因此：

- 有效元素个数为奇数：中位数是 `small.peek()`。
- 有效元素个数为偶数：中位数是 `(small.peek() + large.peek()) / 2.0`。
- 两个 `int` 相加前必须转成 `long`，否则极值输入可能溢出。

注意，写 `small` 包含 `[1, 2, 3]` 表示它负责这些元素，不表示 `PriorityQueue`
内部或迭代结果完全有序。大根堆只保证堆顶是 `3`，内部数组可能是 `[3, 1, 2]`。

## 2. 普通双堆：动态数据流中位数

对应代码：[MedianFinder.java](MedianFinder.java)

### 插入

```text
num <= small.peek()  -> 放入 small
num >  small.peek()  -> 放入 large
然后执行 balance
```

`small.peek()` 是两部分的分界线。按照这个分界插入可以维持顺序不变量，
`balance` 只需恢复大小不变量。

### 为什么 balance 使用 if，不需要 while

每次 `add` 只增加一个元素，并且操作前双堆已经平衡，因此两堆大小关系最多只偏离目标 1。
跨堆移动一次堆顶后，大小差改变 2，立即恢复目标状态。

这个结论依赖前提：**每次单元素操作结束后都调用 balance**。如果批量修改后才平衡，
或者外部可以直接修改堆，则应使用 `while` 或重新证明边界。

### 复杂度

- 插入：`O(log N)`。
- 查询中位数：`O(1)`。
- 空间：`O(N)`。

普通数据流只有插入，没有删除，因此直接使用两个堆的物理 `size()`，不需要延迟删除。

## 3. 为什么滑动窗口需要延迟删除

窗口右移时要执行：

1. 加入右侧新元素。
2. 删除左侧过期元素。
3. 查询新窗口中位数。

Java `PriorityQueue.poll()` 删除堆顶是 `O(log K)`，但 `remove(Object)` 必须先在线性结构中
定位指定元素，复杂度是 `O(K)`。每个窗口都直接删除指定值，总复杂度可能退化到 `O(NK)`。

延迟删除的策略是：

- 元素离开窗口时，立即从**逻辑大小**中扣除。
- 不在线性时间内寻找它，只在 `delayed` 中登记。
- 当失效元素以后到达堆顶时，使用 `poll()` 将其物理删除。

对应代码：[SlidingWindowMedian.java](SlidingWindowMedian.java)

## 4. delayed 的精确定义

```text
delayed: value -> 该 value 还需要从堆中物理删除的次数
```

`delayed.get(value)` 不是窗口中该值的剩余有效次数。比如：

```text
delayed[5] = 2
```

表示已经有两个值为 `5` 的元素离开窗口，但它们对应的两个物理副本尚未从堆顶弹出。

### 为什么 value 可以作为 key

虽然重复值的具体副本无法区分，但它们对大小比较和中位数完全等价。删除任意一个相同值的
物理副本，都能代表删除其中一个已经失效的逻辑副本，因此只需要按值累计次数。

如果业务要求区分对象身份或精确删除特定副本，应使用 `(value, uniqueId)` 作为键，
或者改用支持精确删除的有序表。

## 5. 物理大小与逻辑大小

延迟删除以后，`PriorityQueue.size()` 包含两部分：

```text
物理大小 = 窗口内有效元素 + 已失效但尚未到达堆顶的元素
```

所以必须单独维护：

- `smallSize`：`small` 中有效元素数量。
- `largeSize`：`large` 中有效元素数量。

平衡条件和奇偶判断都必须基于逻辑大小，不能使用 `heap.size()`。

## 6. erase、prune 与 balance 的协作

### erase(num)

1. 执行 `delayed[num]++`。
2. 根据当前有效分界线 `small.peek()` 判断它逻辑上属于哪一侧。
3. 对相应的逻辑大小减一。
4. 如果它正好等于该堆堆顶，立即 `prune`。
5. 调用 `balance` 恢复大小不变量。

重复值跨越两个堆时，按 `num <= small.peek()` 归入 `small` 仍然成立，因为等值副本可以互换。

### prune(heap)

`prune` 只连续检查堆顶：

```text
堆顶不在 delayed 中 -> 停止
堆顶在 delayed 中   -> poll，并将待删除次数减一
```

不需要主动寻找非堆顶失效元素。它现在不会影响中位数；如果将来会影响答案，就一定会先成为
堆顶，届时再删除即可。每个物理元素最多入堆一次、出堆一次，因此总成本可以做摊还分析。

### balance()

`add` 或 `erase` 每次只改变一个逻辑元素，操作开始前又是平衡状态，所以一次跨堆移动足够。
移动堆顶后要 `prune` 原堆，因为原堆暴露出的新堆顶可能已经被标记为失效。

## 7. 复杂度与空间边界

设数组长度为 `N`，窗口长度为 `K`：

- 每个元素至多进入堆一次、被物理弹出一次。
- 时间复杂度：摊还 `O(N log K)`。
- 当前窗口的有效状态：`O(K)`。
- 延迟删除实现的物理堆占用：最坏可能达到 `O(N)`，因为某些失效元素可能长期无法到达堆顶。

如果题目或生产场景要求存储严格限制为 `O(K)`，应考虑支持精确删除的平衡树、
带反向索引的堆，或语言内置的有序多重集合。

## 8. 双堆、SBT 与其他结构的选择

| 场景 | 推荐结构 | 原因 |
| --- | --- | --- |
| 数据流持续插入，只查中位数 | 普通双堆 | 标准库即可，代码短，查询 `O(1)` |
| 固定窗口，只查中位数 | 双堆 + 延迟删除 | 经典解法，摊还 `O(N log K)` |
| 动态插入删除，还要任意第 k 小、排名 | SBT / Treap | 子树大小直接支持 order statistics |
| LeetCode 480，且已经熟练掌握 SBT | SBT `(value, index)` | 精确删除，结构严格保持 `O(K)` |
| 离线数据且值域可压缩 | 坐标压缩 + 树状数组 | 计数前缀和可支持第 k 小 |
| 只维护最大或最小的 Top-K | 单堆 | 不需要双堆的两侧分区 |

SBT 并没有让双堆失去价值：

- 双堆是中位数问题的专用结构，依赖少、实现短，是常见面试标准解。
- SBT 是通用顺序统计树，能扩展到任意第 k 小和排名，但旋转、`size` 维护及删除代码更多。
- 面试时应根据题目需求和可用时间选择自己最稳定的实现，不必为了通用性强行使用更复杂结构。

## 9. 双堆还能用于哪些场景

- LeetCode 295：数据流中位数。
- LeetCode 480：滑动窗口中位数。
- 在线维持固定分位点：通过调整两侧目标大小，让堆顶对应某个秩；需要重新定义平衡比例。
- 流式统计中维护“低半区 / 高半区”的边界。

双堆不适合直接处理任意排名、任意第 k 小、区间计数等通用顺序统计查询；这类需求优先使用
SBT、Treap、树状数组或线段树。

## 10. 对数器与对拍

- **对数器**：生成测试数据、调用待测实现和暴力实现、比较结果的测试程序。
- **对拍**：反复执行两种实现并比较结果的验证过程。

本目录两个 Java 类的 `main` 都是对数器，使用固定随机种子以保证错误输入可以复现。
普通中位数的参照实现是 `List + sort`；滑动窗口的参照实现是逐窗口复制、排序并取中位数。
